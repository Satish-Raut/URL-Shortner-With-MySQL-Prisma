# Authentication Approaches: Session vs JWT

In this project, two primary methods of authentication were explored: **Session-based Authentication** using cookies and **JWT-based Authentication** (Stateless). Below is a theoretical explanation of both approaches and how they were practically implemented in the original code.

---

## 1. Session-Based Authentication

### Theoretical Explanation
Session-based authentication is a **stateful** authentication technique. 

1. **Login:** When a user logs in with valid credentials, the server authenticates the user.
2. **Session Creation:** The server typically creates a session for the user and stores it in the server's memory or a database (in a simpler approach, like the one initially used in this project, simple flags like `isLoggedIn` and `userId` are stored directly as client-side cookies).
3. **Cookie Assignment:** The server sends a unique Session ID (or tracking cookies) back to the client via an HTTP `Set-Cookie` header.
4. **Subsequent Requests:** The client's browser automatically includes these cookies in every subsequent request to the server.
5. **Validation:** The server reads the cookie and identifies the user, thus granting access to protected routes.
6. **Logout:** The server destroys the session from its memory/database and instructs the client to clear the browser cookie.

*Note: In the initial implementation for this project, the cookies were simply storing the raw `userId` and an `isLoggedIn` boolean. While functionally demonstrating the flow, a production-grade session system would typically use a secure, unguessable Session ID mapping to user data on the server side.*

### Practical Implementation

#### A. Login Controller (`auth.controller.js`)
Upon successful credential validation, cookies are set directly to indicate the user is logged in.

```javascript
// ----💡 Session Authentication Approach-------
// 4. Set the cookie only upon successful login
res.cookie("isLoggedIn", true); // Login Status
res.cookie("userId", validUser.id); // To know which user logged In
```

#### B. Middleware (`auth.middleware.js`)
The middleware checks the `isLoggedIn` cookie. If it equals `"true"`, the user is allowed to proceed to the protected route.

```javascript
export const requireAuth = (req, res, next) => {
  // 1. Read all cookies generated by cookie-parser
  const isLoggedIn = req.cookies.isLoggedIn;

  if (isLoggedIn === "true") {
    // User is authenticated, let them access the controller!
    next();
  } else {
    // No valid cookie found, stop the request and send a 401 error
    return res.status(401).json({
      success: false,
      error: "Unauthorized: Please log in to access this resource",
    });
  }
};
```

#### C. Fetching the Current User
Routes fetching user data rely on the `userId` cookie to look up the database.

```javascript
export const getCurrentUser = async (req, res) => {
    const isLoggedIn = req.cookies.isLoggedIn;
    const userId = req.cookies.userId;

    if (isLoggedIn !== "true" || !userId) {
      return res.json({ loggedIn: false });
    }

    const [user] = await getUserById({ id: Number(userId) });
    // Proceed to return user data...
};
```

#### D. Logout
Logout involves clearing the specific tracking cookies.

```javascript
export const logoutUser = async (req, res) => {
    res.clearCookie("isLoggedIn");
    res.clearCookie("userId");
    return res.json({ success: true, message: "Logged out successfully" });
};
```

## 2. JWT-Based Authentication

### Theoretical Explanation
JSON Web Token (JWT) authentication is a **stateless** authentication technique. The server does not keep a record of which users are logged in.

1. **Login:** The user provides their credentials to the server.
2. **Token Generation:** The server validates the credentials and uses a secret key to cryptographically sign a JSON object (payload) containing user details (like `id`, `name`, `email`). This signed string is the JWT.
3. **Token Delivery:** The server sends the JWT back to the client. In this project, it is securely delivered via an HTTP-only cookie (`access_token`).
4. **Subsequent Requests:** The client sends the JWT (automatically via the HTTP-only cookie) with each request meant for a protected route.
5. **Validation:** The server independently verifies the token's cryptographic signature using its secret key. If valid, the server extracts the user's details from the token payload and grants access. No database lookup is strictly required just to know *who* the user is, because the token itself carries this information reliably.
6. **Logout:** The client clears the token (the server clears the HTTP-only cookie).

### Practical Implementation

#### A. Token Generation (`auth.service.js`)
A centralized function builds the token payload and signs it using a secret key.

```javascript
import jwt from "jsonwebtoken";

export const generateTocken = ({ id, name, email }) => {
  return jwt.sign({ id, name, email }, process.env.JWT_KEY, {
    expiresIn: "30d",
  });
};
```

#### B. Login Controller (`auth.controller.js`)
On successful login, the token is generated and securely attached to an HTTP-Only cookie, protecting it from cross-site scripting (XSS) attacks.

```javascript
// ---- 🚀 JWT Authentication Approach-------
// i. Define the token
const token = generateTocken({
  id: validUser.id,
  name: validUser.name,
  email: validUser.email,
});

// ii. Set the cookie here with a token
const isProduction = process.env.NODE_ENV === "production";
res.cookie("access_token", token, {
  httpOnly: true,
  secure: isProduction,
  sameSite: isProduction ? "none" : "lax",
  maxAge: 30 * 24 * 60 * 60 * 1000,
});
```

#### C. Middleware (`auth.middleware.js`)
The middleware reads the `access_token` cookie and verifies its signature.

```javascript
import jwt from "jsonwebtoken";

export const requireAuth = (req, res, next) => {
  const token = req.cookies.access_token;
  if (!token) return res.status(401).json({ error: "Please Login to your account first." });

  try {
    const decoded = jwt.verify(token, process.env.JWT_KEY);
    req.user = decoded; // The payload (id, name, email) is now available in req.user
    next();
  } catch (err) {
    return res.status(401).json({ error: "Invalid/Expired token" });
  }
};
```

#### D. Fetching the Current User
The current user's profile is resolved by verifying the JWT and reading the `id` from the payload to fetch the complete up-to-date user record.

```javascript
export const getCurrentUser = async (req, res) => {
    let token = req.cookies.access_token;
    if (!token) return res.json({ loggedIn: false });

    // Verify JWT token
    const decoded = jwt.verify(token, process.env.JWT_KEY);
    
    // I need only the id of the user who logged in to fetch their details
    const [user] = await getUserById({ id: Number(decoded.id) });
    // Proceed to return user data...
};
```

#### E. Logout
For JWT inside cookies, logout simply involves telling the browser to clear the `access_token` cookie.

```javascript
export const logoutUser = async (req, res) => {
    const isProduction = process.env.NODE_ENV === "production";
    res.clearCookie("access_token", {
      httpOnly: true,
      secure: isProduction,
      sameSite: isProduction ? "none" : "lax",
    });

    return res.json({ success: true, message: "Logged out successfully" });
};
```

## Summary of Differences

| Feature | Session-Based (Initial Project Approach) | JWT-Based (Current Project Approach) |
| :--- | :--- | :--- |
| **State** | Stateful (requires server/client tracking of session state). | Stateless (token itself contains all verification data). |
| **Security** | Susceptible to tampering if raw data like `userId` is stored unprotected directly in cookies. | Highly secure; token is cryptographically signed and tampering invalidates the token. |
| **Storage** | Raw values stored directly in multiple cookies (`isLoggedIn`, `userId`). | Single token payload stored securely in an `HttpOnly` cookie. |
| **Scalability** | Can be harder to scale if server memory/database is heavily relied on to validate sessions. | Easy to scale since the server doesn't need to check a database/memory to authenticate a request. |
